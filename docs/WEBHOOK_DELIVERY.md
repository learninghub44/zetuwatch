# Webhook delivery contract

This document defines the security primitives for future ZetuWatch webhook delivery. It does **not** mean webhook destinations can be configured or that outbound webhook delivery is enabled.

## Signing

Each endpoint will receive a one-time secret generated by `createWebhookSecret()`. The format is `whsec_` followed by 32 cryptographically random bytes encoded as base64url.

For each delivery, sign the exact UTF-8 HTTP request body:

```text
signed_message = decimal_unix_timestamp + "." + raw_request_body
signature = HMAC-SHA256(endpoint_secret, signed_message)
header = "t=" + timestamp + ",v1=" + lowercase_hex(signature)
```

Send the header as `ZetuWatch-Signature`. The receiver must:

1. Read and retain the exact raw request body bytes.
2. Parse exactly one `t` and one `v1` value.
3. Reject timestamps outside the default 300-second tolerance (the verifier permits an explicitly configured tolerance from 30 to 900 seconds).
4. Recompute HMAC-SHA256 over the timestamp and exact raw body.
5. Compare using Web Crypto verification before parsing or acting on the JSON payload.
6. Deduplicate by the immutable event ID in the body. Timestamp tolerance alone does not prevent replay inside the allowed window.

Payloads above 256 KiB are rejected by the signing primitives. Secrets must be displayed once, encrypted at rest when endpoint storage is implemented, excluded from logs, and rotated by creating a replacement secret.

Cloudflare Workers' Web Crypto implementation exposes `crypto.subtle` and supports HMAC signing and verification: https://developers.cloudflare.com/workers/runtime-apis/web-crypto/

## Retry policy

The shared policy allows at most 10 attempts. A network failure or HTTP 408, 425, 429, or 5xx response is retryable. Other 3xx/4xx responses are treated as permanent failures.

The next-attempt delay is exponential from a 30-second base, with 0.5x–1.5x jitter and a six-hour upper bound. The jitter source is injected into the pure function so tests can be deterministic. The dispatcher must persist attempt counts and the next-attempt timestamp before releasing its lease.

## Not yet implemented

The following are still required before the webhook feature can be called complete:

- Tenant-scoped endpoint CRUD, role checks and endpoint secret encryption/rotation.
- An immutable incident-event outbox and delivery records.
- Bounded due-delivery claiming, lease recovery and idempotent attempt persistence.
- A destination egress transport that validates DNS answers, pins the chosen address, validates every redirect hop, enforces HTTPS/ports/timeouts/body limits and resists DNS rebinding.
- Delivery history, UI controls, deletion/retention policy and end-to-end tests.

**Outbound webhook requests must remain disabled** until the egress transport has passed the SSRF and rebinding test suite. Do not replace this gate with an ordinary `fetch(userSuppliedUrl)`.
